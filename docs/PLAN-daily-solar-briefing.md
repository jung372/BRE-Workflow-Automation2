# 태양광 일간 시황 브리핑 구축 계획

작성일: 2026-10-16 · 상태: 설계 승인 및 코드 구현 완료, 운영 연결 대기

기존 BRE Workflow 웹사이트에 **태양광 일간 시황 탭**을 추가한다. 국내 태양광 산업의 주요 뉴스를 매일 수집·검증하여 웹에 게시하고, 태양광 전용 Teams 채팅방으로 요약 알림을 보낸다. 오늘 브리핑, 날짜별 과거 호, 누적 기사 검색을 제공하며 Teams 연결 전에도 웹 조회가 가능하도록 구성한다.

이 문서는 승인된 구축 계획이며 구현된 설정·명령·검증 절차는 [태양광 운영 안내](solar-news-operations.md)를 따른다. 아래 일정과 범위는 설계 기본안이다. 운영 배포와 실제 발송은 별도 실행 단계에서 진행하며 현재 서버 설정과 수신 상태는 연결 단계에서 확인한다.

## 목표와 기본 범위

| 항목 | 기본안 |
|---|---|
| 이용자 | 태양광 개발·사업관리·EPC·운영 실무자 |
| 메뉴 | 공지 모니터링 / 풍력 일간 시황 / 태양광 일간 시황 |
| 콘텐츠 | 국내 태양광 사업·정책·입찰·전력시장·공급망 관련 일간 뉴스 |
| 웹 보고서 | 오늘의 핵심 최대 3개, 사건별 대표기사 최대 15건, 근거가 있는 자체 요약과 원문 링크 |
| Teams | 핵심 최대 5건과 해당 날짜의 태양광 보고서 링크 |
| 기록 | 발간 기사·자체 요약·날짜별 호·정정 이력 지속 보관 및 검색 |
| 발행 주기 | 주말·공휴일 포함 매일을 기본안으로 제시 |
| 운영 방식 | 기존 n8n 인스턴스에 태양광 업무 추가, 공통 Python 처리 코드 재사용 |

1차의 ‘시황’은 산업 뉴스 브리핑을 뜻한다. SMP·REC·모듈 가격 등의 **수치 시계열과 차트**는 출처, 기준시각, 단위, 수집 방식이 확인된 항목부터 후속으로 추가한다. 1차에서도 해당 지표를 다룬 기사는 포함하되 기사 속 수치를 실시간 시장가격으로 표시하지 않는다.

## 현재 구조와 필요한 확장

| 로컬에서 확인한 구조 | 태양광 추가 시 적용 |
|---|---|
| `assets/navigation.js`가 `#/daily`와 날짜·검색 경로를 풍력 화면에 연결 | 풍력 주소를 유지하고 태양광 경로 추가 |
| `news/relevance.py`가 풍력 관련 문맥을 판정 | 산업별 분류·선정 규칙을 설정으로 분리 |
| `news/publisher.py`가 풍력 게시 영역과 전용 clone 경계를 관리 | 태양광 전용 게시 경로와 clone을 지원하고 경로 검증 유지 |
| `news/store.py`가 DuckDB 단일 writer와 호·전달 원장을 제공 | 같은 코드로 태양광 전용 DB 운영 |
| `news/service.py`가 `WIND_NEWS_TEAMS_WEBHOOK_URL`을 참조 | 태양광 실행 환경은 전용 변수만 참조 |
| `news-report.yml`이 공고용 `TEAMS_WEBHOOK_URL`을 풍력 설정으로 동기화 | 태양광 전용 설정 작업과 비밀값을 별도 정의 |
| `configure_teams.py`가 해당 동기화에서 `messagecard` 형식을 지정 | 태양광 수신 흐름에 맞는 카드 형식을 독립 설정·검증 |
| `ci-deploy.yml`이 `data/wind-news/**` 변경을 코드 배포에서 제외 | `data/solar-news/**`에도 같은 제외 규칙 적용 |

풍력 설정을 복사하고 제목만 바꾸면 기사 분류, 게시 경로, 날짜별 발송 제한, 웹훅 동기화가 섞일 수 있다. **공통 코드는 재사용하고 산업별 실행 상태와 설정은 분리**하는 방식을 적용한다.

## 웹 탭과 보고서

| 화면 | 제안 주소 | 표시 내용 |
|---|---|---|
| 태양광 오늘 브리핑 | `#/solar` | 최신 호, 보고서 날짜, 집계 마감, 수집 상태 |
| 날짜별 보기 | `#/solar/dates` | 발간일 목록과 정정 여부 |
| 특정 날짜 보고서 | `#/solar/YYYY-MM-DD` | 해당 날짜의 최신 유효 revision |
| 누적 기사 검색 | `#/solar/archive` | 기간·키워드·기업·프로젝트·지역·분류 필터 |

기존 풍력 즐겨찾기 `#/daily`와 과거 호 링크는 유지한다. 모바일 메뉴에도 두 산업명을 명확히 표시하고, 선택한 탭·검색 조건·날짜를 URL에 반영한다. 태양광 화면의 캐시와 검색 상태는 풍력 화면과 구분한다.

기사에는 제목, 2~3문장 요약, 사업 유형, 기업·프로젝트·지역, 기사시각, 출처, 원문 링크를 표시한다. 사업상 확인할 점은 원문 사실 요약과 구분한다. 금액·설비용량·계약 단계는 원문 근거가 있는 값만 사용한다.

화면 상태는 다음처럼 구분한다.

- 오늘 호 미발간: 이전 호의 날짜와 함께 ‘오늘 브리핑 준비 중’ 또는 ‘발행 지연’을 표시한다.
- 정상 수집 후 적합 기사 0건: ‘오늘의 신규 주요 기사 없음’으로 발간한다.
- 일부 출처 실패: 성공한 출처의 유효 자료를 보존하고 수집 누락을 표시한다. 필수 출처 조건을 충족하지 못하면 발간을 보류한다.
- 파일 조회 실패: 오류와 재시도 기능을 제공한다. 0건으로 표시하지 않는다.

## 수집과 편집 기준

| 분류 | 검색·선정 범위 예시 |
|---|---|
| 정책·인허가 | 태양광 제도, 입지·개발행위, 주민 참여, 영농형·수상형 관련 정책 |
| 개발·건설 | 지상형·지붕형·수상형·영농형, EPC, 착공·준공, 운영 개시 |
| 전력시장·계약 | 태양광 관련 SMP·REC, 고정가격계약, PPA, RE100 |
| 금융·거래 | PF, 투자, 발전소 인수·매각, 계약 체결·해지 |
| 공급망·기술 | 폴리실리콘·웨이퍼·셀·모듈·인버터, 국내 기업의 태양광 사업 |
| 계통·운영 | 접속 용량, 출력제어, 태양광 연계 ESS, 안전·유지보수 |

‘태양광’ 직접 검색과 주제별 검색을 함께 사용한다. 기업명만으로 포함하지 않으며, ESS·PPA·전력망 같은 공통 주제는 본문의 태양광 연관성을 확인한다. 단순 주가 기사, 제품 광고, 태양열·우주 관측 등 다른 분야의 기사는 제외한다. 국내 사업과 국내 기업 관련 한국어 보도를 초기 범위로 두고 해외 전반은 후속 확장으로 둔다.

기존 공개 기사 발견·원문 수집 어댑터를 재사용하되 태양광 검색어와 출처별 적합성을 표본으로 검증한다. 원문 접근 가능 여부, 이용조건, 발행시각과 본문 추출 상태를 확인하고 외부 장애·파싱 실패·정상 0건을 별도로 기록한다. 새 공급원이나 API는 기존 수집원과 같은 조건이라고 가정하지 않는다.

동일 사건은 사업명·지역·주체·발생일·계약 단계와 근거를 대조해 대표기사 한 건으로 묶는다. MOU, 본계약, 금융종결, 착공, 준공, 해지는 서로 다른 단계로 유지한다. 동일 기사가 풍력과 태양광에 모두 관련되면 각 산업 브리핑에 포함할 수 있으나 각 호의 선정과 발송은 독립 처리한다.

요약 후 별도 근거 검증을 통과한 기사만 발간한다. 용량은 MW와 MWh, DC와 AC 기준을 구분하고 단위·기준이 불명확하면 임의 변환하지 않는다. 최소 기사 수를 채우려고 관련성이 낮은 기사를 추가하지 않는다.

## 실행 환경과 데이터 설계

기존 `news/`에 산업 프로필을 도입한다. 프로필은 산업 ID, 검색·분류 규칙, 요약 지침, 공개 경로, 화면 주소, Teams 설정 키를 가진다. 외부 요청으로 임의 경로나 환경변수명을 지정할 수 없도록 `wind`와 `solar`의 허용된 프로필만 사용한다.

1차는 동일 코드에서 태양광 전용 서비스 인스턴스를 실행하는 구성이 적합하다. 풍력 DB 스키마를 대규모로 바꾸지 않고도 수집 실패·발송 상태·복구를 산업별로 관리할 수 있기 때문이다. 실제 포트와 runtime 경로는 서버 점검 후 지정한다.

| 항목 | 태양광 제안 |
|---|---|
| 정책·수집 설정 | `config/solar_news_policy.json`, `config/solar_news_collection.json` |
| DB·로그·작업 원장 | 태양광 전용 runtime, `solar-news.duckdb`, DB별 단일 writer |
| 공개 데이터 | `data/solar-news/index.json`, `latest.json`, 날짜별 불변 호, manifest, 검색 shard |
| 호 ID | `solar` 산업 접두어와 발행일, revision |
| 게시 clone | 태양광 전용 쓰기 가능한 clone, 허용 경로는 `data/solar-news/**` |
| Teams 전달 대상 | 내부 식별자 `solar-daily`, 전용 발송 원장 |
| n8n 작업 이름 | `BRE-SOLAR-*` 접두어로 수집·준비·게시·전달·복구 구분 |

DuckDB에 원천 메타데이터·기사·사건·호·전달 기록을 저장하고 정제·품질검사에는 Polars를 사용한다. 공개 JSON과 검색 자료는 검증된 스냅샷에서 생성한다. 브라우저는 정적 JSON을 읽으며 서버 DB와 n8n에 직접 접속하지 않는다. 기사 전문의 보존기간과 공개 범위는 자체 요약·발간 이력의 지속 보존과 별도로 관리한다.

두 산업이 같은 Git 원격 브랜치에 게시하므로 **clone 분리와 함께 뉴스 게시 작업도 직렬화**한다. 다른 공고 게시 작업과 원격 변경이 겹치면 최신 상태를 동기화하고 자기 산업의 데이터만 다시 반영한다. 강제 push나 다른 산업 파일 복구·삭제를 하지 않으며 제한된 재시도 후 실패 상태를 남긴다.

요약 실행량 증가가 풍력 마감을 밀어내지 않도록 산업별 후보 수·호출 한도·처리 시간을 측정한다. 같은 인증 자원을 공유할 경우 호출 조정과 토큰 갱신 충돌을 검증한다. 태양광 전용 DB와 게시 자료의 백업·복원도 별도 점검한다.

## Teams 전용 입력과 연결

**Teams 채팅방 링크와 메시지 수신용 웹훅 URL은 별개의 입력이다.** 채팅방 정보는 목적지 확인에 사용하고 실제 발송에는 그 채팅방에 연결된 수신 흐름의 웹훅을 사용한다. 웹훅 URL 자체에는 목적지 채팅방을 사람이 확인할 수 있는 정보가 없을 수 있으므로 수신 흐름의 대상 설정도 대조한다.

| 입력 정보 | 입력 시점과 위치 | 용도 |
|---|---|---|
| 태양광 채팅방 이름·종류 | 연결 준비 시 운영자 확인 | 그룹 채팅 또는 채널 구분, 수신 대상 확인 |
| 채팅방 링크 또는 대상 식별 정보 | 필요 시 보호된 운영 설정 | 목적지 대조용, 공개 페이지에 포함하지 않음 |
| 태양광 전용 웹훅 URL | 운영자가 GitHub Actions Secret `SOLAR_NEWS_TEAMS_WEBHOOK_URL`에 직접 입력하는 방식을 기본안으로 채택 | 실제 전송 비밀값 |
| 수신 흐름의 관리 담당·활성 상태 | 연결 준비 시 확인 | 유지보수와 수신 장애 확인 |
| 카드 형식 | `SOLAR_NEWS_TEAMS_CARD_FORMAT` | 수신 흐름에 맞춰 `messagecard` 또는 `adaptive` 결정 |
| 발송 요일·시각 | 운영 설정 | 기본 제안은 매일 08:30 시작 |

입력 절차는 다음과 같이 구현한다.

1. 운영자가 태양광 수신 흐름의 대상 채팅방과 웹훅을 확인하고 전용 Secret에 직접 등록한다. 실제 URL을 대화창·계획서·저장소에 전달할 필요가 없게 한다.
2. 태양광 전용 설정 작업이 Secret을 보호된 표준입력으로 서버에 전달한다. 서버는 전용 runtime 설정에 원자적으로 저장하며 명령 인자·로그·워크플로 산출물에는 값을 남기지 않는다.
3. HTTPS·허용 endpoint·빈 값·개행·BOM 등을 검사한다. 조회 화면에는 설정 여부와 카드 형식만 표시한다. 인증된 내부 운영 경로만 설정을 변경할 수 있다.
4. `preview`는 비밀값 변경 없이 카드·대상 별칭·보고서 링크·기존 발송 상태를 확인하도록 설계한다. 설정 적용 작업과 미리보기 작업을 구분한다.
5. 실제 시험 발송을 요청받은 단계에서 ‘태양광 연결 테스트’ 한 건을 보내고, 수신 흐름 실행 결과와 **태양광 채팅창에서의 표시**를 확인한다. 시험 메시지는 일간 브리핑 발송 원장을 소진하지 않는다.
6. 수신 확인 후 태양광 정기 알림을 활성화한다. 웹훅 교체 시에도 같은 확인 절차를 적용하며 기존 발송 이력을 초기화하지 않는다.

태양광 웹훅이 없으면 `TEAMS_NOT_CONFIGURED`를 표시하고 웹 발간은 계속한다. `TEAMS_WEBHOOK_URL`이나 `WIND_NEWS_TEAMS_WEBHOOK_URL`로 자동 대체하지 않는다. 정적 GitHub Pages에 웹훅 입력란을 두거나 공개 JSON·브라우저 저장소에 비밀값을 보관하지 않는다.

수신 흐름의 카드 계약은 실제 연결 단계에서 확인한다. 현재 풍력의 설정 동기화는 MessageCard를 지정하고 있으므로, 과거 문서의 AdaptiveCard 설명을 태양광에 그대로 적용하지 않는다.

## 발행 일정과 중복 방지

풍력의 현재 문서화된 오전 운영 기준을 참고하여 아래 일정을 태양광 기본안으로 둔다. 시간대는 워크플로마다 `Asia/Seoul`로 지정한다.

| 시간 | 태양광 작업 |
|---|---|
| 정기 수집 | 하루 중 분산 수집, 최근 자료를 겹쳐 조회하며 중복 제거 |
| 07:30 | 전일 07:30 이상부터 당일 07:30 미만까지 집계 마감 |
| 07:40 | 기사 선정·요약·근거 검증·호 확정 |
| 07:50부터 | 게시 큐에서 웹 보고서·검색 자료 발행, 실제 JSON·해시·날짜 확인 |
| 08:30~09:25 | 5분마다 준비·게시·전달 중 미완료 단계 확인 |
| 09:30 | 당일 자동 알림 마감, 미발송·불확실 상태 기록 |

정기 실행 주체는 기존 n8n 한 곳으로 둔다. GitHub Actions는 설정·미리보기·수동 작업 용도로 구성한다. 풍력과 동시에 요약·게시할 때의 소요시간을 측정해 태양광 준비 시작시각을 조정하되 집계 마감과 발송 기준을 운영 설정에 명시한다.

웹 게시 검증을 통과한 당일 호만 Teams에 보낸다. 일간 발송 제한은 산업·수신 대상·서울 날짜·메시지 유형을 기준으로 적용하고, 세부 전달 기록에는 호 ID와 revision을 남긴다. revision 변경이나 웹훅 교체만으로 같은 날 다시 발송되지 않게 한다. 정정 알림은 명시적으로 실행하는 별도 메시지 유형으로 관리한다.

`PREVIEWED`는 카드 검증, `WEB_VERIFIED`는 게시 검증, `ACCEPTED`는 웹훅 접수를 뜻한다. `UNKNOWN`은 수신 결과가 불확실한 상태다. `ACCEPTED`와 `UNKNOWN` 이후에는 자동 재전송하지 않고, 실제 채팅창 표시 확인은 별도 기록으로 남긴다. 전송 전에 확실하게 실패한 경우에만 정해진 시간 안에서 재시도한다.

## 구현 순서와 완료 기준

아래 공수는 현재 구조를 재사용하는 개발·검증 작업의 초기 추정이며, 수신 흐름 준비와 외부 수집원 대응 기간은 별도다.

| 단계 | 작업과 산출물 | 완료 기준 | 추정 |
|---|---|---|---|
| 1 | 태양광 분류·검색어·보고서 fixture, 산업 프로필 설계 | 포함·제외 사례와 실제 없는 샘플 보고서 검토 가능 | 0.5~1일 |
| 2 | 공통 코드 확장, 태양광 DB·수집·검증·publisher | 풍력 회귀 통과, 태양광 데이터·발송 이력 독립 | 2~3일 |
| 3 | 웹 탭·오늘 호·날짜별 조회·검색 | 직접 링크·모바일·빈 상태·오류 상태 확인 | 1~1.5일 |
| 4 | 전용 웹훅 설정·카드·n8n 작업 템플릿 | 미설정 처리와 오발송 방지 모의 검증 통과 | 1일 |
| 5 | 요청된 운영 배포·웹 게시·시험 수신 확인 | 태양광 채팅창 수신, 풍력 정상 동작 확인 | 0.5~1일 |

개발·연결 작업은 약 **5~7.5 작업일**을 예상한다. 이후 7일간 시범 운영하며 기사 적합성, 잘못된 사건 통합, 수집 누락, 오전 마감, 중복 발송을 점검한다. 초기 시범 운영에서는 Teams 자동 발송을 꺼 둔 상태로 콘텐츠를 먼저 확인하고, 시험 수신 확인 후 활성화한다.

주요 수정 대상은 `index.html`, `assets/navigation.js`, 뉴스 화면·검색 모듈, `news/relevance.py`, `news/pipeline.py`, `news/summarizer.py`, `news/dedup.py`, `news/publisher.py`, `news/service.py`, `news/delivery.py`다. 태양광 설정·실행 템플릿·운영 스크립트·테스트를 추가하고 `.github/workflows/ci-deploy.yml`에 태양광 데이터 게시 제외를 반영한다. 공통화 범위는 풍력 회귀 테스트로 확인하면서 좁게 유지한다.

검증 항목은 다음과 같다.

- 저장된 fixture와 모의 응답으로 태양광 관련성, 단위, 계약 단계, 중복 통합, 정상 0건과 수집 실패를 확인한다.
- 풍력·태양광을 같은 날짜에 실행해도 호 ID·작업 키·전달 원장·캐시가 충돌하지 않는지 확인한다.
- 태양광 웹훅 누락·오류 때 풍력 endpoint가 호출되지 않는지, 미리보기에서 전송이 발생하지 않는지 모의 transport로 검증한다.
- `UNKNOWN`, 재시작, 같은 시간 슬롯 중복 호출, revision 변경, 웹훅 교체, 09:30 마감을 검증한다.
- 두 산업 동시 게시와 원격 브랜치 변경에서 다른 산업의 파일·이력이 보존되는지 확인한다.
- 기존 Python 전체 테스트와 관련 프런트엔드 테스트를 실행한다. 키워드 설정·로직 변경 시 프로젝트의 추가 키워드 검증도 실행한다.
- 운영 적용 단계에서는 Pages의 날짜·내용·검색·모바일 탭과 Teams 수신 흐름·실제 채팅창 표시를 각각 확인한다. 기본 테스트에서 실제 수집·push·발송을 실행하지 않는다.

기본 Python 검증 명령은 `python -m unittest discover -s tests -p "test_*.py" -v`다. 오류 시 태양광 워크플로와 발송만 중지할 수 있게 하고, 이전 코드·설정·검증된 태양광 스냅샷으로 복구하는 절차를 운영 문서에 남긴다. 기존 풍력 발간물과 전달 원장은 복구 과정에서도 보존한다.

## 구현 전 확정할 정보

계획의 기본값으로 샘플과 웹 화면 작업을 시작할 수 있다. 실제 연결 시에는 다음 정보를 확정한다.

| 결정 항목 | 기본 제안 또는 필요한 입력 |
|---|---|
| 산업 범위 | 국내 태양광 사업과 국내 기업 관련 한국어 뉴스 |
| 가격 데이터 | 1차는 뉴스 중심, 수치 시계열·차트는 출처 검증 후 추가 |
| 발행 요일·발송 시간 | 매일, 08:30 시작·09:30 마감 |
| Teams 목적지 | 태양광 채팅방 이름·종류와 수신 흐름 담당자 |
| Teams 비밀값 | 연결 단계에서 운영자가 전용 Secret에 입력 |
| 카드 계약 | 수신 흐름에 맞는 형식을 연결 단계에서 확인 |

웹훅 준비가 늦어져도 웹 발간·누적 검색 구축은 진행할 수 있다. 완료 판단은 **태양광 탭 조회, 근거 검증된 일간 발간, 풍력과 독립된 알림, 실제 태양광 채팅창 수신 확인**으로 한다.
